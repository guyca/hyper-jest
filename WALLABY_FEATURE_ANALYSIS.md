# HyperJest: Wallaby.js feature research and parity analysis

This document records what Wallaby.js does in VS Code for Jest projects, how it does it, and how HyperJest reproduces (or deliberately does not reproduce) each capability. It is written for the developer who maintains HyperJest without internet access: every web fact carries the URL it was read from on 2026-10-09, and every local fact carries a file path (with line numbers or byte offsets where the minified sources make lines meaningless). Nothing in here was invented; items that were inferred rather than read are marked **(inferred)**.

Companion documents: the approved implementation plan (`/Users/guyc/.claude/plans/task-research-wallaby-js-nested-snowflake.md`) and `CLAUDE.md` in this repository (hard rules, toolchain, build/package/test commands, repository map, protocol summary, troubleshooting, verification checklist).

## 1. Purpose and sources

### 1.1 Purpose

HyperJest is an offline, license-free, telemetry-free VS Code extension that gives Jest projects a Wallaby-like real-time experience: gutter coverage squares, inline failure messages, inline `console.log` and `//?` values, native Test Explorer integration, on-type and on-save incremental runs, debugging and snapshot commands. Wallaby 1.0.502 is installed on the development machine, so its manifest and core are the ground truth for parity decisions. This analysis is the reference that the parity decisions were made against.

## 2. How Wallaby works

### 2.1 Process topology

Wallaby is two programs: the editor extension and a local "core" server, versioned and updated separately (the extension from the Marketplace, the core by download into `wallaby1d8e3b/`; https://wallabyjs.com/docs/v1/intro/how-it-works.html). Whenever a tracked file changes the editor sends the diff to the core, the core applies it to its own cache of source files and runs the affected tests; `node_modules` is never copied.

- **Core spawn.** `client.js` L14 `@3775`: `spawn(nodePath, ["--harmony", server.js, "extended-core-ws", ...flags, "--customNodeVersion=" + (WALLABY_NODE ? 1 : 0)])`, where `nodePath = process.env.WALLABY_NODE || "node"` (`@1843`) and `WALLABY_NODE` comes from the `wallaby.node` setting. The child `PATH` is extended with `/usr/local/bin:/usr/bin`; `NODE_ENV` and `NODE_PATH` are deleted.
- **Test workers.** `server.js` L334 `@418891-420312`: `child_process.spawn(env.runner, [...env.params.runner flags, server.js, "runner", "nodeTestWorker", workerId, receiverPort, frameworkVersion, frameworkPath, nodeModules, originalCacheRoot, regeneratorRuntime, configFile, logLimits, toolVersion], {cwd, env})`. The worker is *spawned, not forked*: there is no Node IPC channel. The env is `process.env` plus `env.params.env`; `ELECTRON_RUN_AS_NODE` is deleted unless `WALLABY_ELECTRON_RUN_AS_NODE` is set.
- **Framed JSON over stdio.** Messages are `"###wms###" + JSON + "###wme###"`; core to worker via `stdin.write` (`_sendToWorker`, L334 `@427937`), worker to core via stdout, errors via stderr; markers inside payloads are escaped (`@428625`). Message types: `in:run`, `in:stop`, `in:teardown`, `in:ping`/`pong`, `in:tracer.resume`, `in:connected`, `closed` (L334 `@422359`, `@432548`).
- **Worker hardening.** `process.exit` is replaced with a no-op (`const b=process.exit;process.exit=function(){}`, L334 `@~429700`); the worker uses `exitWhenParentExits()`; a ping timeout triggers a worker recycle (L791 `@766641`, "Received timeout starting test run, recycling worker").
- **Other channels.** A WebSocket receiver on 127.0.0.1 with a random port for browser runners and the tracer (L791 `@731923`); a result-cache child `spawn(process.execPath, [server.js, "resultCache"], {stdio:[…,"ipc"]})` (L793 `@792234`); a generic processor pool `fork(e, ["worker"])` sized `os.cpus().length` (L773 `@550208`).

### 2.2 Zero-config Jest: Wallaby uses Jest's own `readConfigs`

`loadJest` (`server.js:795 (col 5)`): read the project `package.json`; if `scripts.test` contains `react-app-rewired` use CRA's `createJestConfig`; if `devDependencies.jest` exists or `scripts.test` contains `jest` (and not `react-scripts`) use plain Jest. Resolve `jest` from `testFramework.path`, the react-scripts location, or the project dir; **`jest-cli` must be resolvable** ("Module jest-cli is not found in '<dir>'"); require Jest major >= 24 (`col 1460`). Then call `jest-config`'s **`readConfigs()`** with `{config: testFramework.configFile}` if set, else the CRA config, else `{}` and the project dir. Jest itself therefore resolves `jest.config.{js,ts,mjs,cjs,json}` or the `package.json` `jest` key, presets, transforms, `moduleNameMapper`, setup files and `projects` (https://wallabyjs.com/docs/integration/jest/). `jest.config.ts` is loaded through Wallaby's bundled ts-node in `transpileOnly` mode with `@swc/wasm` (`jestTsNodePatch`, `col 4820`). Only projects whose `runner` is `jest-runner` or `jest-runner-groups` are kept (other runners are silently dropped; "Can not find any Jest runner configurations in '<dir>'" if none remain).

From the Jest config (`server.js:331`, cols 2900-6000) Wallaby derives: always-ignored paths (`/node_modules/` at any depth, root `dist/`, `build/`, `coverage/`, `worktrees/`, any dot-folder, `.watchman-cookie`); `android/` and `ios/` only when the root `package.json` `dependencies` (not devDependencies) contains `react-native` (`col 2931`); `files` from `roots`, `tests` from `testMatch`/`testRegex` plus `testPathIgnorePatterns` and `modulePathIgnorePatterns` ("Can not autodetect test patterns, neither Jest testMatch nor testRegex is set." at `col 5687`); `collectCoverageFrom` becomes `filesWithCoverageCalculated` and `coveragePathIgnorePatterns` becomes `filesWithNoCoverageCalculated` (so RN+TS projects need `ts,tsx` in `collectCoverageFrom` or source files show no indicators, https://github.com/wallabyjs/public/issues/3217); `hard.noCompilers = true` (Jest's transforms do all compilation) and `env = {type:'node'}` (`col 5950`). A separate extractor process (`node <flags> <core> extractor jest {...}`, JSON between `####-WALLABY-MARKER-START-####` markers) is used when the runner node differs from the core's node or `env.params.*` is set (`server.js:331 (col 963)`).

Docs-level config facts: `autoDetect` default `true`; the docs say the order is `['vitest','angular','jest','node:test']` while the code default is `["angular","jest","vitest","node:test","python"]` with vitest promoted to the front when it is a declared dependency (`server.js:276 (col 1655)`); `autoDetect: ['jest']` forces Jest (https://github.com/wallabyjs/public/issues/3349). Config lives in `wallaby.js` or a `"wallaby"` key of `package.json`, is read once at start, and overrides go through `setup(wallaby){ wallaby.testFramework.configure({...}) }` where `setupFilesAfterEnv` and `transformIgnorePatterns` are concatenated and every other key replaces the project value (`INIT:57 col 7705`; issue #2393).

### 2.3 Running at real paths with `fs.readFileSync` redirection

In zero-config Jest mode Wallaby runs Jest at the user's **real paths**: runner paths are `localRoot + path` (`selectRunnerFile`, `WS:787 @597991`) and the worker cwd is the project root (`WS:334 @417739`). Only the legacy non-autoDetect mode runs against an instrumented copy tree; every `instrumented/` directory in the five cached projects on this machine holds 0 files.

Unsaved and changed content reaches the worker like this:

1. The editor sends patches; `_writeFileChanges` (`WS:790 @640119`) applies diff-match-patch patches or a full replacement, writes the full content to `~/.wallaby/cache/projects/<hash>/original/<rel>` (`_writeSourceFile @656062` always writes for zero-config Jest), marks the file `inOriginalFilesCache` and bumps `changeTs`.
2. The `in:run` message carries `{path, id, ts, inOriginalFilesCache, logMarkers, …}` per file into `global.$_$tracer._filePathToFileData` (`WS:334 @433434`).
3. In the worker, `fs.readFileSync` is patched (`WI:57 @39745`): if the path has file data with `inOriginalFilesCache`, `arguments[0]` is rewritten to `path.join(originalCacheRoot, t.path)` before calling the original. graceful-fs clones `fs` at first require and Jest is loaded later inside `initializeJest`, so the clone picks up the patched function **(inferred from load order)**. `fs.writeFileSync` is patched (`@39954`) to turn inline-snapshot writes into `tracer.sendFileChange`.
4. Jest's mtime-based `getScriptCacheKey` is replaced with `${path}_${workerId}_${id}_${ts}` (`tracer._fileCacheKey`, `WI:57 @38455`; patch list `WI:14 @3685`), and the transformer's `getCacheKey` is extended with `'W' + fileId + md5(sorted logMarker ids)` (`_extendJestTransformer @40346`). Example on disk: `runnerCacheKey 'a20f6ee29890e4d2cb8200585854d249W20'`.
5. **Nothing patches `fs.statSync`, `existsSync` or `realpath`** (grep count 0 in `initializer.js`, `server.js`, `tracer.js`, `register.js`). Import targets must exist on disk at their real path; only their content can come from the cache. A brand-new unsaved file that exists only in the cache can execute, but its unsaved new imports fail resolution **(inferred)**.

### 2.4 In-band execution through `createTestScheduler`

Wallaby does not call `runJest` and does not drive jest-circus directly. Per run (`configure`, `INIT:57 @32952`):

```js
jestConfig.globalConfig.updateSnapshot = tracer.canUpdateSnapshots() ? "all" : process.env.CI ? "none" : "new";
const t = Object.assign({}, jestConfig.globalConfig, {$_$session: global.$_$session});
testRunner = await createTestScheduler(t, {changedFiles: [], sourcesRelatedToTestsInChangedFiles: []});
```

The run body (`@36500-38200`) calls `clearDefaultResolverCache()`, unshifts the `WallabyRunner` reporter, builds `tests` via `getTestData`, interrupts the previous `WallabyWatcher`, and runs `scheduleTests(l, wallabyWatcher)` inside an `AsyncLocalStorage` session. Because `globalConfig.maxWorkers = 1` (`@32098`) and `workerIdleMemoryLimit` is deleted (`@32443`), `shouldRunInBand` is true (v29 `@jest/core/build/testSchedulerHelper.js:50-56`), the scheduler passes `{serial:true}` (`TestScheduler.js:245-247`) and jest-runner's `#createInBandTestRun` calls `runTest` **inside the Wallaby worker process** (`jest-runner/build/index.js:68-112`). So Jest's own parallelism is always off; Wallaby's worker pool provides it (https://github.com/wallabyjs/public/issues/3358).

Forced `globalConfig` fields (`INIT:57 @28200-32560`): `notify=false, bail=0, collectCoverage=false, detectLeaks=false, detectOpenHandles=false, errorOnDeprecated=false, json=false, maxWorkers=1, useStderr=false, watch=false, verbose=null`, `watchman=false` when `NO_WATCHMAN` is set; deleted: `findRelatedTests, listTests, forceExit, onlyChanged, onlyFailures, outputFile, passWithNoTests, watchAll, watchPlugins, testResultsProcessor, reporters, workerIdleMemoryLimit`. Per project config: `bail=0, notify=0, collectCoverage=false`, `setupFilesAfterEnv ||= []` with Wallaby's own setup file prepended, `transformIgnorePatterns \|\|= []`, ts-jest `diagnostics=false` unless explicitly true and `sourceMap:true` forced; `watchPlugins`, `testResultsProcessor` and `reporters` deleted. Environment (`INIT:14 col 2499`): `BABEL_ENV ||= 'test'`, `NODE_ENV ||= 'test'`, `JEST_WORKER_ID = workerId+1` (and the line `process.env.JEST_WORKER_ID = '1';` is patched out of `jest-runner/build/index.js`, `INIT:14 @11207`).

Contexts: `testContextByConfig` is module-level (`INIT:57 @32574`); `getTestData` (`@34787-35009`) lazily does `jestRuntime.module.createContext(r, {maxWorkers, watchman})` with no `watch` option and never rebuilds it during the process lifetime **(inferred: no other writer)**. Each file maps to a project config by `testMatch`/`testRegex` plus the longest `rootDir`/`roots` match, fallback `configs[0]` (`col 8815`). Per run only `clearDefaultResolverCache()` runs, and jest-resolve's `checkedPaths` cache is disabled (`checkedPaths.get = function(){}`, `WI:14 @6659`). On each `in:run` the worker deletes `Module._cache` entries under the project root (`SRV:L334 @433550`). `globalSetup`/`globalTeardown` are executed by Wallaby itself ("Failed to run jest globalSetup: …", `INIT:57 col 9832`), with `require.cache` entries for tracked files deleted first (`@35426`).

Cancellation: `WallabyWatcher` (`INIT:57 @32602`) has `interrupt()` setting `_isInterrupted` and `isWatchMode(){return true}` (so `bail` never calls `exit()`). In-band jest-runner checks `watcher.isInterrupted()` before each file and throws `CancelRun` (`jest-runner/build/index.js:81-83`). Mid-file cancellation comes from the patched circus (`jestCircusSkipTest` returns true when `global.$_$session !== p`, `INIT:56 @20299`), stale async work is fenced with async_hooks + AsyncLocalStorage (`INIT:14 @700-2600`), and hard hangs are handled by ping-timeout recycling.

### 2.6 Instrumentation and per-test bitset coverage

Wallaby's own instrumentor (`server.js:334`, acorn 8.17.0 + acorn-jsx + acorn-walk, escodegen-wallaby) runs **after** the project transformer by wrapping `process()`/`processAsync()` (`WI:57 @40346-46041`): normalise the inner map, `new SourceMapConsumer`, call `utils.instrument(code, {file:id, test, testFileChangeStart, recordValues, captureConsoleLog, logMarkers mapped original→transformed, extractedComments})`, build `lineMap = updateFileMap({}, [transformerMap, instrumentMap])`, send `sendTransformedFile`, then `n.code = t.code; delete n.map; n.wallaby = true` so Jest receives no source map and Wallaby maps stacks itself. With no transformer a dummy `process(){return {code:null,map:null}}` instruments the raw source.

Probe shapes (`_scopeStartVariableDeclaration @400207`, `_instructionCallExpression @390883`, `_wrapIntoVisitor @387093`): `var $_$c = $_$wp(fileId)` per program, `$_$wf(fileId)` per function, `$_$w(fileId, rangeIdx, $_$c)` per statement, `$_$wv(fileId, rangeIdx, 'fileId,rangeIdx', $_$c, '<expr text ≤40 chars>', <value>, <eval exp or '$_$ne'>, flag, flags, {permanent:1, traceId, changeId})` for values; `console.log(a, …)` becomes `$_$tracer.log(a, …, '<arg0 source text>', fileId, rangeIdx)` (`_replaceConsoleLog @381348`); a two-element sequence expression `(a, b)` becomes `$_$tracer.diff(a, b, "a vs b", file, rangeIndex)`.

Per-test hits are a **bitset over test ids**, with no diffing step (`tracer.js` line 14): `_statement(e,t){ $_$coverage[e][t][this._spec.index] |= 1<<this._spec.bitPosition }` (`col ~6013`); `specStart(id, …)` sets `_spec={id, name, index:id>>>5, bitPosition:31&id}` (`col ~7113`); `specSyncStart` records the first hit as the test's declaration range (`col ~7427`); `specEnd` and `reset` return to spec id 0, which means "outside any test" (`col ~7720`, `@~18756`). `scopeStart(fileId)` appends to `_fileEncounterSequence`, attached as `e.files` at `result(e)` (file-level "executed by test", `col ~10185`). `programScopeStartLoading`/`EndLoading` record per test file the files evaluated while it was loading (`_testLoadingSequence`, `col ~6268-6821`): the source of `testFilesLoadedFrom`. The server receives `coverage` messages `{id:fileId, ranges}` (`@~9000-9900`), an inverted index range → tests.

Instrumentation is also what makes test declaration lines known: declarations come **only from runtime results** (`processCoverageResult`, `server.js:790 (col 751-1521)`; `declaration=p` assigned only when the runtime `testRange` matches an instrumented range and `_looksLikeTestDeclarationRange` holds, `col 4591`/`7693`). Duplicate names get `name #N` (`"Test name duplicate: "` log). The acorn pass only records `_testNames` (literal or expression-free template titles of `it`/`test`/`asyncTest`), `fit`/`fdescribe`/`.only` focus and `matchSnapshotRanges` (`col 104688`, `@350300`, `@351557`); it does not build a test tree before a run.

### 2.8 Worker defaults and recycling

`_calculateNumberOfParallelWorkers` (`server.js:791 (col 56066)`, `@737530`): `initial = workers.initial || max(cpus-2, 2)`, `regular = workers.regular || max(floor(initial/2), 2)`, each at least 1, PhantomJS capped at 16; the log line is "Parallelism for initial run: X, for regular run: Y". ### 2.10 Run modes, Pause, Zen Mode

`runMode` has exactly two values, `automatic` (default, stored as `"auto"`) and `onsave` (https://wallabyjs.com/docs/config/overview/#run-mode-automatic--on-save; `server.js:790 (col 31520)`, `:787 (col 12961)`). A config `runMode` wins and is not persisted; otherwise the per-project dynamic setting `run.mode` is used and persists across restarts. In `onsave` mode in-editor changes only invalidate markers. Commands in the manifest: `wallaby.runModeOnSave` ("Change Run Mode to On Save Only") and `wallaby.runModeImmediate` ("Change Run Mode to On Any Change (Automatic)"), both `when wallaby.live && !wallaby.paused`; they are the **only** run-mode commands among the 112 `contributes.commands` entries (title listing of `package.json` with `node -e`). The labels "Make Current Session Run on Any Change", "Make Current Session Run Only on Save" and "Toggle Current Session Run Mode" appear only on the docs page https://wallabyjs.com/docs/intro/vs-code/#run-mode; no command with any of those titles exists in 1.0.502, so they are docs-only names (possibly entries of Wallaby's own quick-pick palette, not verified), not additional extension commands. `wallaby.runOnSaveIndicators` (true) shows last-run (hollow) indicators in on-save mode. **There is no on-demand mode**; the nearest equivalents are Pause (`wallaby.pause`: stops real-time execution, hides editor artifacts, queues changes and runs only affected tests on resume, https://wallabyjs.com/whatsnew/pause.html), Smart Start `startMode: 'never'|'edit'`, Exclusive Test Run, `runSelectedTestsOnly`, and the Run Line/File/Project commands. Zen Mode hides coverage indicators and inline errors while tests keep running, stored per project (https://wallabyjs.com/docs/intro/vs-code/#zen-mode). `delays.run` default 0 and `delays.edit` default 100 ms (`:288 (col 2331)`).

### 2.11 Smart Start and Exclusive Test Run

Smart Start (`wallaby.smartStart`, https://wallabyjs.com/docs/features/smart-start/, https://wallabyjs.com/docs/config/smart-start/): only the test files you are working on run; the `smartStart` config is an array of `{startMode, pattern}` where the first match wins, `pattern` defaults to `**/*`, and `startMode` is `open` (default; run a test file when it is opened), `edit` (run after it is edited), `always` (run on start) or `never` (manual add only). `always` entries are ignored when starting an Exclusive Test Run. `wallaby.startAutomatically` (true) restarts in the same mode; Wallaby never auto-starts a project where it was never started, or that never returned results, and `Stop` disables auto-start for that folder (v1 tutorial). Variants: `wallaby.smartStartOnClosestMonoRepoProject`, CLI `wallaby --smart`.

Exclusive Test Run (https://wallabyjs.com/docs/features/selected-tests/#exclusive-test-run): `Start Exclusive Test Run` / `Add to Exclusive Test Run` on a file or folder (explorer and editor-title context menus, `package.json` L758, limited to js/jsx/ts/tsx/coffee/vue/python files excluding `wallaby*.js` and `jest.config.js`, and folders other than `.idea/.vs/.vscode/node_modules`). For Jest, Webpack and Angular CLI it only processes the selected files; it resets when Wallaby stops; `Run Project Tests` resets it. Test selection by `.only`/`fit`/`fdescribe` and the comments `// file.only` / `// file.skip` (`hints.testFileSelection`, `automaticTestFileSelection`, `runSelectedTestsOnly`) also narrows execution; filtering (Toggle Test Filter) only limits what is displayed.

### 2.12 The v3 engine

https://wallabyjs.com/docs/features/streaming-caching/ and https://wallabyjs.com/blog/wallaby-v3.html: asynchronous event-driven architecture; result streaming (tests, coverage, logs, errors appear as produced); cached results shown instantly at startup for unchanged test files and re-verified in the background (the `resultCache` child); prioritisation queues tied to editor events (open test and source files first, then failing tests, then tests related to recent edits); edits during a run cancel and re-queue only the affected batches; progress indicators and time estimates in the Status tab.

### 3.3 Live comments (https://wallabyjs.com/docs/features/advanced-logging/#live-comments)

| Marker | Effect |
|---|---|

### 3.4 Hovers and compact diff

**Why the deferred items are deferred.** The Time Travel Debugger, Test Story and Profiler all depend on Wallaby's own instrumentor, which rewrites every statement into a `$_$w(fileId, rangeIdx, $_$c)` probe and records an ordered trace with values (`maxTraceSteps` 999,999). HyperJest reuses the project's istanbul instrumentation instead, which yields hit counters, not a sequence, and keeps the user's transform cache byte-for-byte; adding a trace would mean a second instrumentation pass on every file and a trace store per test, which conflicts with the latency and memory budget of the warm-worker design. Value Peek / Show Value need an on-demand expression injection and re-run cycle that is reasonable to add on top of `probeTransformer` later. The AI tools and MCP server are excluded by the offline, no-telemetry requirement. The webview panels were traded for native surfaces (Test Explorer with profiles, hovers, Problems, status bar, virtual documents) that need no React bundle and no theme forwarding.

- **shono `jestConfig.js` is cwd-bound and side-effectful** (`@wix/shono-testjs/dist/src/jestConfig.js`): `rootDir = process.cwd()`, reads `./package.json` at require time, sets `process.env` (`RNTL_SKIP_AUTO_CLEANUP`, `TZ=UTC`), stubs a plugin in `require.cache`, calls `patchFiles()` which rewrites files in `node_modules` (including `node_modules/jest-runtime/build/index.js`, idempotent via `.BACK` copies), and exports `exports.default` with three inline `projects` (Legacy Unit `**/?(*.)+(spec|test).legacy.[jt]s?(x)`, Unit `unitTests/**/*.spec.ts?(x)` + `src/**/*.spec.ts?(x)` (+ `tests/**` in 9.136), Headless `headlessTests/**/*.spec.ts?(x)`), a custom resolver (`packageFilter` swapping `main` for the `react-native` field; a likely no-op under v30's `unrs-resolver`), the `jestPreprocess.js` transformer (babel-jest `createTransformer`, reads cwd inside workers), `modulePathIgnorePatterns:['dist']` (matches any path containing "dist"), `haste {defaultPlatform:'ios', platforms:['android','ios','native']}`, `modulePaths [rootDir, <engine>/node_modules]`, `resetModules/resetMocks/restoreMocks: true`, a headless `globalSetup` that may run `yarn install`, custom reporters and a `testResultsProcessor`. The CLI runs `RNTL_SKIP_AUTO_DETECT_FAKE_TIMERS=true NODE_OPTIONS=--max_old_space_size=4096 USE_HEADLESS_PB=true [NODE_PATH=$NODE_PATH:<engine>/node_modules:<cwd>/node_modules] <jest from shono-testjs dir> -c <shono-testjs>/dist/src/jestConfig.js` (`index.js:84-125`). `NODE_PATH` is read once when jest-resolve loads, so one process cannot serve two shono packages. Wallaby sidesteps the problem rather than reproducing the CLI: each generated per-package `wallaby.js` (e.g. `packages/modules/wix-one-app-account/wallaby.js`) sets `autoDetect: true`, `testFramework.configFile` to a shono `jestConfig.js` and `env.params.env` to only `RNTL_SKIP_AUTO_DETECT_FAKE_TIMERS=true NODE_OPTIONS="--max_old_space_size=4096"`, with **no `NODE_PATH` and no `USE_HEADLESS_PB`**, and one Wallaby session serves one package (see the Wallaby-vs-CLI mismatch below). HyperJest resolves the same chain the CLI does, sets the full CLI environment, and spawns one worker per package with cwd = package dir.
- **Mixed hoisting means "resolve by chain, never by `.bin` or hoisted siblings"**: engine root `jest-config`/`jest-circus` 29.7.0 vs `jest` 30.4.2; mobile-modules root `.bin/jest` 30.2.0 vs effective 29.7.0. Jest's `jest/bin/jest.js` goes through `import-local`, which switches to a nested `jest` resolved from `process.cwd()`, so cwd must be the package dir.
- **Jest's implicit resolution rule** (29.7 `resolveConfigPath.js:136-176`, 30 `index.js ~2543`): at each dir collect `jest.config.{js,ts,mjs,cjs,json}` (v30 adds `.mts,.cts`) plus `package.json` if it has a `jest` key; more than one → "Multiple configurations found"; otherwise return the config, or the `package.json` even without a `jest` key (**the nearest `package.json` terminates the walk**); `rootDir` defaults to the config dir; `config.cwd = realpath(process.cwd())`. Wallaby defers to this rule entirely (section 2.2); HyperJest applies it as flavor (c) after shono and script-selected configs.
- **Wallaby's own answer to monorepos** is manual: `Select Configuration` with "closest project in mono-repo" (walks up from the active editor looking for `package.json`, `jest.config.js`, …), `Start on closest project in mono-repo`, and one session per project (https://github.com/wallabyjs/public/issues/2970, #3536). Its RN `android/`/`ios/` ignore checks only the `dependencies` of the `package.json` of the project it was started on (`server.js:331 (col 2931)`). Verified on 2026-10-09 with `node -e` over the eight repo-root `package.json` files: none lists `react-native` under `dependencies` (or `devDependencies`), so a Wallaby session started at a repo root would not ignore `android/`/`ios/`; the practical effect on its file watcher is **(inferred)** from the code and was not tested.
- **Known Wallaby-vs-CLI mismatch in mobile-modules** (not a HyperJest concern, but it explains result differences between the two tools): every generated `wallaby.js` points at `./../../../node_modules/@wix/shono-testjs/dist/src/jestConfig.js`, i.e. the **root** `@wix/shono-testjs` **9.134.0**, while `shono testjs` resolves `@wix/shono 9.1568.0 → nested @wix/shono-lib 9.258.0 → nested @wix/shono-testjs 9.136.0`. 9.136 adds the `customNodeEnv.cjs` test environment, `coverageProvider: 'v8'` when `collectCoverageFrom` is set, and the `tests/` unit folder (`UNIT_TESTS_FOLDER_NAMES ['unitTests','tests']`), so Wallaby and the CLI run different configs in the same package; `wix-one-app-home-feed/wallabyUnit.js` additionally uses a wrong relative path (`./../../node_modules/...`, one level short). Legacy `wallaby.conf.js` / `wallabyJest.js` files (marketing, media-manager) call `w.testFramework.configure(require('./package.json').jest)`, and media-manager's `package.json` has no `jest` key. HyperJest follows the CLI chain (9.136.0) and ignores every `wallaby*.js`.
- Test-file volume: about 1,760 Jest test files (mobile-modules legacy 16 + unit 790 + headless 365; engine ~470; relops 66; delay-of-game 55), ~16.7k `it/test` and ~5k `describe` call sites; `.each` in 156 files, template-literal titles in 57, `.skip/xit/xdescribe` in 159, `.todo` in 20, `.only`/`.concurrent`/`.failing` in 0, `@jest-decorated` in 3, Flow in 0 test files.

## 7. HyperJest architecture (condensed from the plan)

```
Extension host (never loads Jest)                 Worker processes (project's node, cwd = package dir)
 extension.ts                                       dist/worker/hyperjestWorker.cjs  (warm, long-lived, 1..k per project)
  ├ discovery/*  projectRegistry, packageScanner      ├ overlayFs: fs.readFileSync patch installed before Jest loads
  ├ workerPool.ts  N = max(1, cpus-1), affinity,      ├ jestChain: jest → jest-cli → @jest/core → jest-config/-runtime/-runner/-watcher
  │               hot spare, recycle, ping            ├ warmEngine: readConfigs once → stable copies → lazy Runtime.createContext
  ├ runner.ts      queue, generations, cancel         │             → TestRunner.runTests(tests, watcher, {serial:true}) per run
  ├ overlay.ts / changeAnalyzer.ts / core/affected.ts ├ transformHooks: prototype seams (env wrap, //? probe wrap, cache prune)
  ├ core/testParser.ts (@babel/parser) → testTree.ts  ├ envWrapper: per-test coverage diffs, console/value capture, cancel, locations
  ├ decorations.ts / diagnostics.ts / hover / lens    ├ depGraph: hasteFS + DependencyResolver → forward graph
  ├ results/resultStore.ts                            └ cliEngine: spawn node [--require overlayPreload.cjs] <jest>/bin/jest.js --reporters=reporter.cjs
  └ debug.ts / snapshots.ts / statusBar.ts / doctor  dist/worker/{reporter,overlayPreload}.cjs (dependency-free; also used by js-debug launches)
```

*The diagram uses the plan's module names; the **Modules** paragraphs below give both the plan's list and the repository's actual file names.*

**Invariants.** The host never requires a Jest config or Jest internals; every Jest package is chain-resolved from the project's `jest`; zero network and telemetry (`scripts/check-no-network.sh` greps `dist/` for `http/https/net/dns/tls/fetch` and asserts with `lsof` that the extension host and workers opened no sockets); `core/*` and `worker/*` never import `vscode` and are unit-tested with Jest 29.7 + ts-jest.

**Engines.** `hyperjest.engine = auto | warm | cli`. *Warm* (default): one long-lived in-band worker per project slot (Wallaby latency). *CLI*: a fresh `jest/bin/jest.js` per run with the dependency-free `reporter.cjs` (public API only; also used for Debug and Doctor's "Compare with plain Jest"). *auto* falls back to CLI when a warm seam is missing (degraded mode: file-level coverage, `testNamePattern` narrowing, `testLocationInResults` via argv, visible warning).

**Modules as planned** (plan §Module list; this is the planned layout, not a description of the repository): `extension.ts` (activate: `LogOutputChannel` "HyperJest", settings, registry, pool, runner, stores, UI, commands; deactivate → `pool.shutdownAll()`), `settings.ts`, `core/protocol.ts` (`PROTOCOL_VERSION`), `core/{scriptSniffer,shono,jestResolver,nodeResolver,projectSpec}.ts` (pure discovery), `core/testFileMatcher.ts`, `core/{testParser,testIds}.ts` (`@babel/parser` typescript+jsx → describe/it tree with ranges, modes, `.each`, snapshot lines; ids `projectId\0relPath\0kind:title[#dup]…`), `core/{resultModel,affected}.ts`, `discovery/{packageScanner,projectRegistry,configCache}.ts`, `workerPool.ts`, `runner.ts` (`RunCoordinator`: priority queue, dedupe, generations, cancel-and-requeue, `buildRunSpec()`/`buildDebugConfig()` snapshot-tested for v29 and v30), `overlay.ts`, `changeAnalyzer.ts`, `results/resultStore.ts`, `decorations.ts`, `diagnostics.ts`, `hover.ts`, `codeLens.ts`, `statusBar.ts`, `testTree.ts`, `debug.ts`, `snapshots.ts`, `doctor.ts`, `commands.ts`, `log.ts`; `worker/{hyperjestWorker,jestChain,warmEngine,transformHooks,envWrapper,coverageDiff,probeTransformer,depGraph,stacks,cliEngine,reporter,overlayPreload}.ts`. Host → worker: `init {projectId, packageDir, repoRoot, configArg?, jestPkgDir, cliFilters, flags, slot}`, `run {runId, tests:[{path, names?}], updateSnapshot, priority, reason}`, `cancel`, `overlay {changes:[{path, text|null}]}`, `invalidate {reason:'files'|'config', paths}`, `graph`, `showConfig`, `listTests`, `ping`, `shutdown`. **Project discovery** (host, static; the worker's `ready` is the truth): `findFiles('**/package.json', excludes)`; repo root = nearest ancestor `package.json` with `workspaces`; package dir PK = nearest `package.json` dir and **cwd for everything**; Jest package if deps include `jest`, a script invokes `jest`/`shono testjs`, or `jest.config.*`/`jest` key exists (`node --test`, mocha and detox/e2e packages are listed in Doctor as not-jest/e2e). Flavor precedence: (a) shono (resolved like the CLI, env + `NODE_PATH`, `--max-old-space-size=4096`, loaded lazily on first use with `patchFiles()` logged once), (b) script-config (`jest -c <file>`, `--testPathIgnorePatterns=`, env prefixes; one spec per config), (c) implicit (Jest's traversal rule; >1 → `multipleConfigs`), (d) root `projects`. Jest via `require.resolve('jest/package.json', {paths:[PK]})` (missing → `unavailable`; < 29 → unsupported). Node via `hyperjest.nodePath` → version files → fnm/nvm/volta/asdf/n/Homebrew → PATH → `process.execPath` + `ELECTRON_RUN_AS_NODE=1`, validated against Jest engines.

**On-type overlay.** `onDidChangeTextDocument` (file scheme; js/jsx/ts/tsx/json/snap in a ready project) → `overlay.set(fullText)` + dirty ranges → hollow icons → debounce `onTypeDebounceMs` 300 → `changeAnalyzer` (old/new parse diff → whole file or single test) → enqueue. Untitled buffers are save-only. Save clears the overlay entry.

**Affected selection** (`core/affected.ts`). Test file: edit strictly inside one test body with names/function count unchanged → `{path, names:[fullName]}`, else whole file; always add previously failing tests. Source file: `execBy[file]` (per-test runtime hits; narrowing by the edited function is not enabled yet, see §8 item 12) ∪ `loadedBy[file]` ∪ inverse static closure for test files without runtime data ∪ failing tests ∪ global-error files; empty → "no tests cover X"; before any data → CLI `--listTests --findRelatedTests --json`. `.snap` → owning test file. Toolchain files → `invalidate{config}`. Add/delete/rename → `invalidate{files}`. Cap `liveRun.maxTestFilesPerEdit` 8 (remainder demoted to on-save priority). Priorities: explicit 0 > active spec 1 > on-type affected 2 > on-save 3 > visible 4 > smart start 5. Newer edits cancel in-flight runs of the same file.

**UI mapping.** Gutter: one decoration type per state × {solid, hollow} × {plain, camera}, `setDecorations(type, [])` for every empty bucket, refreshed on `onDidChangeVisibleTextEditors`; declaration lines coloured from test status unless `gutter.testDeclarations:'auto'` and `testing.gutterEnabled` (VS Code owns that glyph). Inline: section 4. Test Explorer, Problems, status bar, hover, Doctor: section 4. Contributed colours `hyperjest.inlineError.foreground` (`#c80000`/`#fe536a`), `hyperjest.inlineLog.foreground` (`#0000ff`/`#569cd6`), `hyperjest.inlineValue.foreground` (`#7a5d00`/`#d6b33b`) with high-contrast variants.

**Settings.** 55 keys under `hyperjest.*` (`contributes.configuration.properties` in `package.json`, counted with `node -e`; the plan's §Settings lists 54 when the five `colors.*` keys are counted individually, the one key added during implementation being `hyperjest.tsJest.diagnostics`). The defaults that mirror Wallaby are in the parity matrix (section 4) and the full list with defaults is `contributes.configuration` in `package.json`.

**Build and offline strategy.** `esbuild.mjs` bundles `src/extension.ts → dist/extension.js` (node22, cjs, `external:['vscode']`) and `hyperjestWorker, reporter, overlayPreload → dist/worker/*.cjs` (node18; only HyperJest code and `@babel/parser` are bundled, every Jest/Babel/istanbul module is `require(<chain-resolved absolute path>)`). `.npmrc`: `registry=https://npm.dev.wixpress.com/ save-exact=true ignore-scripts=true audit=false fund=false update-notifier=false` (no `omit=optional`: `@esbuild/darwin-arm64` is an optional dependency and esbuild resolves its binary via `require.resolve`). `npm run package` = `tsc --noEmit` ×2 → `esbuild --production` → `vsce package --no-dependencies --no-yarn --skip-license --allow-missing-repository --no-rewrite-relative-links -o hyperjest.vsix` (`--no-yarn` keeps corepack away from registry.npmjs.org; vsce's TTY-only `npm show` update check swallows errors). Install: `code --install-extension hyperjest.vsix --force` → Reload Window. Building may use the Wix registry; **using** the extension never touches the network.

## 8. Limitations and roadmap

**Known limitations (by design or pending execution).**

1. Warm in-band reruns leak by design: Jest refuses them in watch mode "to prevent watch mode crashes caused by leaks". Mitigated by RSS/run-count/idle recycling, a hot spare and per-project caps, not eliminated.
2. Three prototype seams are private names (`requireAndTranspileModule`, `_getTransformer`, `_cache.transformedFiles`). Each is presence-checked and degrades to file-level data + CLI engine with a visible warning. Wallaby carries the same risk at larger scale (dozens of text patches with v29 and v30 anchors).
3. `__coverage__` diffs and `mode='skip'` narrowing were verified by reading code, not by execution, until their milestone spikes (M5/M4). `test.concurrent` is forced serial (0 uses in the repos); async work escaping a test window lands in the file-level bucket (over-selects, never under-selects).
4. The overlay requires the file to exist on disk (`getScriptCacheKey` stats it; v29 `resolve` stats it; v30 `unrs-resolver` is native). Untitled buffers and unsaved *new* imports are save-only, exactly as in Wallaby.
5. Files outside `rootDir` (sibling packages via `moduleNameMapper`, ~2.6 % of edges in `wix-one-app-member-view`), `__mocks__`, json and setup files are never instrumented (`shouldInstrument.js:101-179`, `test-exclude` refuses files outside cwd); `jest.mock()` calls are not graph edges (the haste extractor never captures them). These get file-level selection only.
6. Static discovery misses helper-registered or dynamic tests (shown as runtime-only children after a run); `.each` and loop rows share one location because `testLocationInResults` is the `test()` call site.
7. shono's `jestConfig.js` runs `patchFiles()` into `node_modules` when first loaded, identical to `shono testjs`; HyperJest loads it lazily and logs it once.
8. Node selection depends on fnm paths; branded-apps' 20.19.4 is not installed, so it warns and falls back. The extension host's PATH `node` is a leftover fnm multishell symlink (v24.19.0) and `--use-on-cd` never runs there, so `.nvmrc` must be, and is, resolved explicitly.
9. Running HyperJest and Wallaby on the same project double-runs tests.
10. Rebuilding the extension needs the Wix registry (or the `~/.npm` cache / symlink fallback to `mobile-apps-relops-automations/node_modules`); the installed `.vsix` never needs the network.
11. Inline rendering differences versus Wallaby: no argument-context prefix on `console.log` values, hover diff rendered as a code block rather than a coloured grammar, no live-updating side-by-side diff.
12. Source-file edits select every test that executed the file (`execBy`), not only the tests that executed the edited function. Function-level narrowing needs coverage metadata keyed by the unsaved text and a stable function identity across edits; until then HyperJest over-selects, never under-selects.
13. While a test file has an unrecoverable syntax error, Run Line / Debug Line / Update Snapshot at line look the test up in the last parse that succeeded. If the breaking edit also shifted lines, the lookup can pick a neighbouring test or the whole file.
14. Discovery's file walk and `package.json` parsing (about 120 ms on mobile-modules) still run on the extension-host thread; Node version probing is cached and asynchronous.

**Roadmap** (prose summary; the plan's milestone list with its per-milestone "Demo" acceptance criteria is reproduced in section 9). M0 scaffold + toolchain → M1 discovery, Doctor, static Explorer → M2 warm engine + file runs (inline errors, Problems, status counts, file-level gutter) → M3 CLI engine, Debug, on-save, static affected selection, pool policy, Smart Start → M4 on-type overlay (single-test narrowing, hollow stale icons) → M5 per-test coverage + 5-state gutter + Coverage profile → M6 console, `//?`, hover, side-by-side diff, Esc chords → M7 snapshots, flavor hardening (shono, engine RN, `jest.config.ts`, package.json-jest, nested serverless jest, branded-apps degradation, node selection, `--findRelatedTests` fallback), `notMatched` → M8 polish (perf: host main thread < 10 ms per IPC batch, 16 ms coalescing), code lenses, keybindings, `check:no-network`, docs, final `hyperjest.vsix`. Post-0.1 candidates, in rough order of value per effort: Toggle Uncovered Regions (data already in `coverageMeta`), Jump to Snapshot (definition provider over `.snap` keys), live-updating side-by-side diff with `onDidChange`, Show Value / Value Peek on top of `probeTransformer`, cached results across restarts, an `edit` Smart Start mode, a Test Story viewer if an ordered trace is ever recorded, and a profiler via the CLI engine with `--cpu-prof`.
